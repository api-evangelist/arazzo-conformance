# Arazzo Conformance

How the open-source [Arazzo](https://spec.openapis.org/arazzo/latest.html) tooling judges valid and invalid
Arazzo documents. Report: **https://arazzo-conformance.apievangelist.com**

Each case is a small Arazzo document that is either valid or breaks exactly one rule. Every tool runs against
every case and is scored on one question: did it call the document valid or invalid, and was it right?

- **schema** cases are decided by the official OAI JSON Schema for that version.
- **semantic** cases break a rule that only the spec's prose states (unique `stepId`s, `operationId`s that
  resolve, runtime expressions that parse, `goto` targets that exist). No schema can catch these, so they
  separate a validator from a schema check.

## Cases

| Set | Where | Count |
|---|---|---|
| OAI schema tests, Arazzo 1.0.1 and 1.1.0 | `cases/oai/<version>/{pass,fail}/` | copied unmodified, pinned in `cases/oai/SOURCE` |
| API Evangelist cases, Arazzo 1.0.1 and 1.1.0 | `cases/ae/<version>/` + `manifest.yml` | generated by `scripts/build-ae-cases.py` |

The AE cases are one valid base document plus one mutation each; the manifest records the rule, the spec
section, and whether the schema or only the prose decides it. Where the official schema and the prose
disagree, the prose wins and the case carries a `note`. Two do today, including a 1.0 schema defect that
rejects the documented object form of a Criterion's `type`. A rule the prose states only as SHOULD is not a case.

The 1.1.0 cases exercise `$self`, step `timeout` and `dependsOn`, AsyncAPI send/receive steps with
`correlationId` and `$message`, success-action `parameters` and `targetSelectorType`, against
`cases/ae/sources/orders.asyncapi.yaml`; the OAI's 1.1.0 tests already cover those fields' schema rules.

OAI's `characterization-*` cases pass the schema on purpose while breaking a rule stated in prose, so a
validator is expected to call them invalid. The three 1.0.1 example documents OAI files under `pass/` break
prose rules too (runtime expression syntax, a non-JSONPath condition, a non-string `value`), so `run.py`
expects them invalid and says why.

## Execution

`cases/exec/1.0.1/` holds whole workflows a runner executes against `scripts/mock-petstore.py` (port 4010, the
`servers` URL in the petstore source). The mock logs every request; a case states the outcome (success or failure),
the exact request sequence, and values the requests must carry, so a runner is judged on what it sent, not on what it
reports. Covered: output chaining, inputs, payload replacements, query and header parameters, success criteria
(simple, regex, body comparison), onSuccess end and goto, onFailure retry (with and without criteria, and an
exhausted retryLimit) and goto, and a step that runs another workflow. `contested` cases are run and shown, never
scored: a JSONPath filter over an object body passes under the spec's own example and fails under RFC 9535, and the
other way round over an array.

`run-exec.py` drives the `runners:` in `tools.yml`. A runner's exit code is not trusted blindly: Arazzo Runner exits
0 on a failed workflow, so its adapter reads the status it prints.

## Tools

`tools.yml` lists each tool, the command, and how to read its result. A tool's verdict is its exit code
(0 = valid). Two patterns refine that: `error` marks a crash, and `unsupported` marks a tool declining
the document's Arazzo version. Declines are shown as "version not supported" and never counted as a pass
or a fail. `claims` records the versions a tool says it supports; a score outside them is labelled "not claimed".
Tools with `role: loads` only parse what they will run, so a pass there means "loaded" and not
"checked".

To add a tool, add an entry to `tools.yml` and re-run.

## Running

```sh
T=$PWD/.tools
mkdir -p $T/node && (cd $T/node && npm init -y && npm pkg set overrides.@speclynx/apidom-ls=2.11.7 && npm i @stoplight/spectral-cli @redocly/cli @jentic/arazzo-validator ajv ajv-formats js-yaml)
python3 -m venv $T/py && $T/py/bin/pip install arazzo-runner pyyaml
GOBIN=$T/go go install github.com/speakeasy-api/openapi/cmd/openapi@latest
$T/py/bin/python scripts/build-ae-cases.py      # only after editing the cases
$T/py/bin/python scripts/run.py --tools $T      # validation: results/<date>.json, docs/data/latest.json
$T/py/bin/python scripts/run-exec.py --tools $T # execution: results/exec-<date>.json, docs/data/exec-latest.json
```

## Not yet covered

- Execution of 1.1.0 workflows (AsyncAPI steps need a broker), workflow `outputs` values, and `dependsOn` order.
- Tools without a published CLI: usearazzo `arazzo-toolkit`, libopenapi's arazzo package, itarazzo (Java).
